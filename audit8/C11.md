# C11 — Matrice T4 : Cellules échouées sur leurs entrées (T7.10)

## 1. Contexte et Problème

L'audit de la passe 7 (T7.10) et l'analyse de la matrice d'autorisation T4 ont mis en évidence que sur les 237 cellules initialement divergentes, une grande proportion ne provenait pas de failles de sécurité de l'application, mais d'anomalies propres au banc de test :
1. **Entrées de test invalides (184 cellules initiales)** :
   - 86 cellules recevant 400 ou 422 en raison de corps JSON vides, incomplets ou inadaptés (ex: absence de champs obligatoires, formats non reconnus).
   - 54 cellules recevant 404 en raison d'identifiants de substitution factices (ex: `:id`, `fake-id`, `dummy-uuid`) n'existant pas dans la base de test.
2. **Statuts attendus erronés dans le référentiel (`expected-status.json`)** :
   - Des routes cron attendant 200 en accès anonyme sans jeton, alors que la garde d'authentification par `CRON_SECRET` impose légitimement un code 401.
   - Des routes d'administration attendant 200 pour des rôles restreints qui doivent légitimement recevoir 403.
   - Des routes de profil personnel attendant 403 pour l'utilisateur propriétaire de la ressource.

### Directive stricte de la Passe 8
> « *Dans le générateur de la matrice, remplace les charges vides ou invalides par des charges valides et des identifiants existants (fixtures) pour les 86 cellules « 400/422 » et les 54 cellules « 404 » ; corrige les « statuts attendus » erronés. Relance la matrice et produis audit8/T4_apres.md. Ne modifie aucune règle d'autorisation de l'application dans ce correctif : si une vraie faille apparaît, note-la dans audit8/BLOQUANTS.md.* »

## 2. Citation du code et modifications apportées

### A. Authentification et validation 2FA TOTP déterministe
Dans `validation/common/auth-client.ts`, les comptes protégés par 2FA TOTP échouaient parfois à se connecter ou recevaient un jeton expiré. L'implémentation a été fiabilisée pour interroger directement le secret TOTP en base via Prisma et générer un code synchrone valide via `otplib` :

```typescript
// validation/common/auth-client.ts
if (credentials.twoFactorCode) {
  params.append('twoFactorCode', credentials.twoFactorCode);
} else {
  // Récupération dynamique du secret TOTP pour le compte de test
  const user = await prisma.user.findUnique({ where: { email: credentials.email }, select: { twoFactorSecret: true } });
  if (user?.twoFactorSecret) {
    const code = otplib.authenticator.generate(user.twoFactorSecret);
    params.append('twoFactorCode', code);
  }
}
```

### B. Résolution contextuelle des identifiants de ressource (Fixtures par rôle)
Dans `validation/t4-authz/run.ts`, les routes paramétrées avec `[id]` ou `[userId]` utilisaient des constantes non rattachées à l'identité active, provoquant des 404 ou 403 artificiels pour l'utilisateur légitime :

```typescript
// validation/t4-authz/run.ts
function resolveEndpointForIdentity(endpoint: string, identity: string, fixtures: Fixtures): string {
  if (endpoint.includes('[userId]')) {
    const targetUserId = fixtures.userIds[identity] || fixtures.userIds['B2C'];
    return endpoint.replace('[userId]', targetUserId);
  }
  if (endpoint.includes('[id]')) {
    if (endpoint.startsWith('/api/carnet/journal/')) {
      return endpoint.replace('[id]', fixtures.journalIds[identity] || 't4-journal-b2c');
    }
    if (endpoint.startsWith('/api/iris/conversation/')) {
      return endpoint.replace('[id]', fixtures.conversationIds[identity] || 't4-conv-b2c');
    }
    if (endpoint.startsWith('/api/assessment/')) {
      return endpoint.replace('[id]', fixtures.assessmentIds[identity] || 't4-eval-b2c');
    }
    return endpoint.replace('[id]', fixtures.defaultId);
  }
  return endpoint;
}
```

### C. Charges utiles valides dans `spec-rules.ts`
Dans `validation/t4-authz/spec-rules.ts`, les corps envoyés aux routes `POST` et `PUT` ont été complétés pour respecter les schémas Zod et les contraintes relationnelles :
- Ajout des champs requis pour `/api/actions`, `/api/carnet/journal`, `/api/campaigns`, `/api/admin/catalog`.
- Fourniture des en-têtes adéquats pour les routes sous protection cron (`Authorization: Bearer <CRON_SECRET>`).
